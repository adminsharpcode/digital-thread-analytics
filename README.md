A lineage backbone for the end-to-end data science lifecycle, applied to
predictive maintenance on the AI4I 2020 dataset.

The idea is borrowed from manufacturing. A *digital thread* is the continuous,
authoritative record that connects every representation of a product across its
whole lifecycle. Data science has the same problem and mostly does not solve it:
raw data, cleaned data, features, experiments, models, deployments and
monitoring live in separate tools, and no single record connects them. MLflow
tracks experiments and now links datasets to logged models; DVC versions data
and models; OpenLineage standardises job-and-dataset lineage for data
pipelines. None of them spans validation outcomes, feature definitions, serving
events and drift observations as one graph you can walk in both directions.

This project builds that connective layer — the **Thread Ledger** — and then
measures what it buys.

Then open <http://127.0.0.1:8000>. Everything else:

## The app

`python run.py serve` starts one Uvicorn process that serves both halves: the
API under `/api`, and the dashboard that consumes it at `/`. The backend holds
no state — it opens a short-lived ledger connection per request, so a pipeline
run that rebuilds the ledger is picked up without a restart.

| Endpoint | Returns |
|---|---|
| `GET /api/health` | whether anything is deployed, and which model |
| `GET /api/overview` | deployment, dataset, feature set, drift, ledger counts |
| `GET /api/models` | every candidate with its metrics, and which was promoted |
| `GET /api/validation` | the data quality checks and their verdicts |
| `GET /api/drift` | the latest drift report, PSI per feature |
| `GET /api/nodes?type=` | browse the ledger |
| `GET /api/trace/{id}` | provenance: everything an artifact depended on |
| `GET /api/impact/{id}` | the other direction: everything it affected |
| `GET /api/graph` | the whole ledger as nodes and edges |
| `POST /api/predict` | score one reading, with its lineage attached |

Interactive API docs are at `/docs`, generated by FastAPI from the same code.

The dashboard has four panels: a live prediction form, the candidate
comparison, per-feature drift against the threshold, and a lineage explorer
that walks any artifact in either direction and reports how long the query
took. A prediction response carries the deployment's node id, so the
"Trace this prediction back to raw data" link turns an answer into its full
provenance in one more call. That round trip is the project's claim made
operable.

## Layout

```
thread/            the contribution — a tool-agnostic lineage ledger
  ledger.py        append-only SQLite graph, content-addressed nodes
  context.py       data / code / environment fingerprinting
  query.py         CLI: stats, show, trace, impact, explain-model, export
  viz.py           self-contained HTML render of the graph
app/               the HTTP layer — API and dashboard
  main.py          FastAPI: /api/* endpoints over the ledger, serves the page
  static/          the frontend: index.html, app.js, styles.css (no framework)
pipeline/          the seven lifecycle stages, one function each
  s1_ingest.py     fetch, fingerprint, validate
  s2_clean.py      clean, profile
  s3_features.py   domain features from the documented failure mechanisms
  s4_train.py      candidates, metrics, optional MLflow
  s5_evaluate.py   compare, gate, promote
  s6_serve.py      batch scoring (the web surface lives in app/)
  s7_monitor.py    PSI drift + the retrain feedback edge
  flow.py          orchestration (plain Python, plus an optional Prefect flow)
baseline/          the control condition: same models, no thread
experiments/       the comparative evaluation
tests/             ledger properties, stage logic and the API
config/config.yaml one configuration for the whole lifecycle
```

## How the ledger works

Three decisions carry the design.

**Content-addressed identity.** A node's id is a digest of its type, name,
version and content digest. Re-running an unchanged stage produces the *same*
id rather than a duplicate, which is what makes the reproducibility measurement
meaningful rather than circular.

**Append-only at the storage layer.** SQLite triggers reject `UPDATE` and
`DELETE` on both tables. A run's status is not patched onto its node when it
finishes; a new outcome node is written and linked. Lineage that can be quietly
rewritten is not evidence.

**One edge direction.** Every edge points backwards in time, from an artifact to
what it depended on, following the W3C PROV convention (`wasDerivedFrom`,
`wasGeneratedBy`, `used`). Because the direction is uniform, a single traversal
function is correct for the whole graph: follow edges outward for provenance,
inward for impact.

Node types: `dataset`, `validation`, `feature_set`, `code_rev`, `environment`,
`run`, `model`, `evaluation`, `deployment`, `prediction_batch`, `drift_report`.

Edge types: `DERIVED_FROM`, `VALIDATES`, `TRAINED_ON`, `BUILT_FROM`, `RAN_IN`,
`PRODUCED_BY`, `EVALUATES`, `PROMOTED_FROM`, `SERVED_BY`, `OBSERVED_ON`,
`TRIGGERS_RETRAIN`.

The ledger stores MLflow run ids, DVC hashes and file paths as plain attributes
and works whether or not those tools are installed. That is the point: it is a
layer over the ecosystem, not another competitor in it.

## Results

From `python -m experiments.evaluate_framework --repeats 5`, on a replica of the
dataset (see the note below), 10 000 rows, 3.39 % positive class:

| Measure | Thread | Baseline |
|---|---|---|
| Reproducibility rate | 100 % over 5 runs | not measurable |
| Lineage completeness | 100 % (6/6 terminal artifacts reach raw data) | 0 % |
| Trace a deployed model | 0.2 ms | manual archaeology |
| Trace a drift report | 0.35 ms | manual archaeology |
| Ledger writes | 82 writes, 0.037 s | — |
| Instrumentation cost | 1.9 % of comparable runtime | — |
| Content fingerprinting | 0.3 % of comparable runtime | — |
| End-to-end, like for like | +23.8 % | baseline |
| Footprint | 60 KB for 32 nodes / 50 edges | — |

The gap between the 1.9 % spent writing lineage and the 23.8 % end-to-end
difference is not lineage overhead: it is the cost of persisting intermediate
artifacts, profiles and feature specifications that the baseline script keeps
only in memory and then discards. That is a fair price to name honestly rather
than hide.

Model results on the case study: random forest reaches PR-AUC 0.734 /
ROC-AUC 0.960 against logistic regression at PR-AUC 0.269, and is promoted
automatically. The simulated drift (60 minutes of additional tool wear, 8 %
higher torque) produces PSI 2.56 on tool wear, far above the 0.20 threshold,
and the monitor writes the `TRIGGERS_RETRAIN` edge that closes the loop.

## A note on the dataset

The pipeline downloads the AI4I 2020 Predictive Maintenance Dataset from the UCI
repository (DOI 10.24432/C5HS5C). Where that download is unreachable — an
offline machine, a corporate proxy — `dataset.allow_synthetic_fallback`
generates a replica from the dataset's published description instead: the
documented marginal distributions of the process variables, the five failure
mechanisms, and the documented 3.39 % failure rate.

**A replica is not the dataset.** Set `allow_synthetic_fallback: false` and
download the real file before producing any result you intend to publish. The
ingestion stage records which of the two was used as an `origin` attribute on
the dataset node — the framework's own principle applied to itself.

## Reference

Ledger API, in full:

```python
from thread import ThreadLedger

with ThreadLedger("artifacts/thread_ledger.db") as led:
    with led.run("my_stage", code_rev="abc123", alpha=0.5) as run:
        node = run.node("dataset", "sales", version="v1", digest=d, rows=1000)
        run.produced(node)              # node PRODUCED_BY this run
        run.used(other, "TRAINED_ON")   # this run TRAINED_ON other

    led.upstream(node)      # everything it depends on
    led.downstream(node)    # everything it affects
    led.trace(node)         # grouped provenance bundle
    led.stats()             # node and edge counts
```
